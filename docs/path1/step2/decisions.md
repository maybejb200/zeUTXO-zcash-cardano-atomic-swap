# Step 2 design decisions (answered from first principles; continue step-1 D1–D16)
- S2-D1 Network rules: Zcash txs are v5, branch NU6.2 (mainnet-active from height 3,364,600; NU6.3 has no mainnet height in zcash_protocol 0.10), Orchard bundle orchard_v2, circuit FixedPostNu6_2. Matches step-1 D11.
- S2-D2 External signatures need alpha, which the plain orchard Bundle builder hides, so all Zcash txs go through the orchard PCZT roles (build_for_pczt → extract_effects → ZIP-244 sighash → finalize_io → create_proof → apply_signature → extract → apply_binding_signature). Honest txs use only these library paths; the library refuses a bad external signature (InvalidExternalSignature).
- S2-D3 Cheating Zcash txs are assembled by hand from parts (bypassing the library's own checks) so the *simulated node's* verifier has to be what catches them, not our builder.
- S2-D4 Simulated Zcash node = parse + canonical re-encode, v5/branch, Orchard-only, anchor ∈ historical roots, nullifiers fresh, fee ≥ ZIP-317 (5,000 × max(2, actions)), then orchard BatchValidator (Halo2 proof + all spend-auth sigs + binding sig) against the ZIP-244 sighash recomputed from the tx. Commitment tree is our own depth-32 tree from the crate's Sinsemilla hash, with filler notes. Not simulated: blocks/PoW/reorgs, mempool policy, expiry (we set 0).
- S2-D5 Step-1 Aiken validator reused byte-for-byte (hash 9000d11d…). The D15 inclusivity note stays open (bounds treated as stated).
- S2-D6 Go-signature handling: Bob gives Alice only the Redeem tx BODY to sign (its script_data_hash commits to the redeemer containing b but does not reveal b). If Bob sent the full tx (with b) first, Alice could take the ZEC with a+b and still Refund at T1. So Bob never shares the witness set before submitting; exunits are fixed into the body by Bob's local evaluation.
- S2-D7 The Lucid emulator does not run Plutus scripts on submit (only at build). So our ledger wrapper re-runs phase-2 on every submitted tx (UPLC eval against the real resolved inputs, actual ≤ declared exunits) and checks fee ≥ minimum, value conservation, required signers, validity interval. Cheaters force-build failing txs with a fake evaluator so the wrapper, not the builder, must reject them.
- S2-D8 Sim timing: Δ = 60 s (Cardano slot = 1 s); T0 = 150 s (ZEC funding deadline), T1 = lock + 250 s, T2 = lock + 350 s. Meets T0 ≥ 2Δ, T1 ≥ 3Δ+1, T2 − T1 ≥ Δ+1. Zcash confirmation depth Z = 3 simulated blocks.
- S2-D9 Amounts: Bob's genesis note 1.0 ZEC; funding 0.5 ZEC to the joint address (change back, fee 10,000 zats); sweeps send 0.5 ZEC − 10,000 zats to the sweeper's fresh wallet. ADA locked: 1,000 ADA.
- S2-D10 Sweep modes: "solo" (spec path: reconstruct σ(a+b) after learning the other share from Cardano) is used in every outcome. "joint" (2-party nonce commit) and "adaptor" (pre-sig + completion) are demonstrated as alternatives in the happy path only and checked valid, not mined.
- S2-D11 Strict-ledger checks, in order: validity interval (lower ≤ slot < ttl), max tx size, inputs exist and unspent, value conservation, declared exunits ≤ per-tx max, fee ≥ minFeeA·size + minFeeB + script fee (mainnet prices), key-locked collateral ≥ 150 % of fee, script_data_hash recomputed (redeemers + datums + PlutusV3 cost model), phase-2 UPLC evaluation against the real inputs (actual ≤ declared), then the emulator's own signature / required-signer checks. A phase-2 failure is simply rejected (a real node would consume collateral; Bob/Alice never submit a failing tx honestly, so this only affects cheaters).
- S2-D12 BUG found and fixed (not a design flaw): wallet key generation started its retry loop from an all-zero seed, which is a valid key, so every party got the same wallet. Caught in the smoke run (Alice and Bob showed identical balances). Fixed with fresh_seed() (random fill before the validity loop); all reported runs are after the fix. Joint-key shares (a, b) were never affected (separate generator).
- S2-D13 BUG found and fixed (tooling): CML.calc_script_data_hash_from_witness returned undefined, so the wrapper rejected every script tx as "PPViewHashesDontMatch", i.e. early cheat rejections were for the wrong reason. Fixed by calling calc_script_data_hash explicitly with the language list taken from the witness scripts. All reported runs show the intended rejection reason per cheat.
- S2-D14 Alice's go-sign policy (checked on the Redeem BODY before signing): it spends exactly the escrow UTxO, spends none of Alice's own UTxOs, has an upper bound with POSIX time ≤ T1 − 1, Alice is not within Δ/2 of T1, and she has seen the agreed ZEC amount at the joint address at depth ≥ Z. If any fails she does not sign and waits for T1 to Refund.
- S2-D15 Bob's broadcast policy: Bob broadcasts the Redeem (which reveals b publicly) only while now + Δ ≤ T1 − 1 s. Reason: if b became public but the Redeem then expired, Alice would hold a+b (take the ZEC) and could also Refund at T1, so Bob would lose the ZEC. Under the Δ delivery bound a Redeem broadcast within this window always confirms. Not an honest-loss flaw, but it is a hard rule for Bob's software and depends on Δ really bounding Cardano inclusion.
- S2-D16 Time scale: simulated chains move in seconds, not hours. Real-world parameters must be re-derived from real Δ (Cardano inclusion under congestion) and Zcash depth; the inequalities in S2-D8 are what carries over.
