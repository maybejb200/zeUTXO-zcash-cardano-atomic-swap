## Why the previous operating model failed

- The team selected the next task from the latest runtime failure, rather than from the largest threat to a usable product. Distinct patches accumulated into one unbounded investigation.
- Parallel helpers, adapters, harnesses and reports increased unfinished integration work while the critical architecture remained unproved. Component success and source preparation were too easy to mistake for delivery progress.
- The proof decomposition made 652 leaf positions distinct fixed relations/keys. Full grouping, parent/key counts, setup management, peak live memory, bootstrap and steady-state throughput were not established before investing in backend tuning.
- Repeated historical handoffs each described a different “next” task. A source edit during handback also demonstrated that author completion and execution freeze were not enforced consistently.
- The usage floor became a work target. Account-wide rounded usage cannot provide exact per-chat cost accounting; available credits or a reset cannot justify continued spending.

### Common statement and state graph

The common public statement is a canonical `(network, genesis, consensus epoch, policy/key version, offer commitment, session, escrow origin/token, funding effects and note/auxiliary outpoint, approved claim/refund effects and fee variants, shielded principal/recipient commitments, outcome kind, outcome transaction/block anchor, selected tip/work/history root)` tuple. Fix effect-bearing randomness and every permitted fee variant before offer commitment; fee replacement may change only explicitly approved fields while retaining the same input, note/nullifier, principal, recipient and terminal kind. A new arbitrary transaction hash is not an authorized variant. Derive the session after deposit from the offer and actual unarmed reference; Arm uses both ledger-checked owner signatures. The existing [versioned interface](R2-SETTLEMENT-INTERFACE.json) defines these identity and transition fields, but is not runtime authority.

`Pinned public genesis and verified epoch transitions -> authenticated header/context updates -> unique live relay token (tip, cumulative work, history commitment, context, policy) -> proved outcome transaction/effects and inclusion -> anchored certificate/ancestry to current selected tip -> StageOutcome(Pending, full ADA principal, available challenge data, staging upper bound + W) -> permissionless better-work branch update/invalidation or FinalizeOutcome against the live relay -> exact Bob payout for claim / exact Alice return for refund, token burn.` The initial relay state needs a genesis proof under the actual network rules, followed by every required link or a separately proved continuity mechanism; a fixture root, recent checkpoint, custom tree root or source RPC assertion cannot initialize it. Each header update must authenticate serialization/hash, Equihash/target, parent, cumulative work, difficulty and median-time context, commitment layout and consensus upgrades (including network exceptions). Proving headers does not revalidate every shielded authorization/nullifier transition: the specified light-client model relies on honest validating miners for included transaction validity. The transaction relation itself still proves its exact receipt/effects and selected-block inclusion. A fork update presents the divergent ancestor and complete valid higher-work suffix/context, then updates the *single* relay UTxO; equal or duplicate work does not refresh age. No prover-controlled root or detached certificate enters the accepted path.

The terminal relation extends R1 `outputs/encryption-primitives/src/effects.rs` and `full_linked.rs` plus R2's synthetic [terminal relation](R2-TERMINAL-RELATION.md): prove the actual Ironwood v6 transparent F and C/R auxiliary input/output, ZIP 244 identities, funding note and terminal nullifier/common principal, complete Sapling/Orchard/transparent effects, correct full encrypted shielded receipt and committed amount/destination. Claim and refund consume the same agreed funding; absence of a claim is never a refund proof. Private note/encryption openings remain private. Before Arm, Alice durably holds everything needed to prove Bob's compatible refund without his later key/service; before any usable claim share/signature/permit escapes, Bob has independently verified settled Arm and durably holds everything needed to prove Alice's compatible claim without her later cooperation. R2 `work/r2/refund-native`, UID custody and exact-byte recovery supply boundaries to adapt; their current saved witness extraction does not yet establish this custody. Never recover by reading old private witnesses or replaying spent signing nonces.

Stage must expose complete public header/certificate/branch/context bytes or a specified retrievable, retained data surface with an enforceable availability condition; a digest or the detached codec alone does not start W. It binds an immutable candidate to the live selected relay at source depth, uses a finite staging interval and sets `notBefore` from its **upper** bound. Relevant higher-work competing history can invalidate the anchor and return the unchanged principal/token to Armed; valid descendants preserve the timer, and invalid or duplicate challenges cannot reset it. Finalization atomically references the unique current relay input and checks ancestry, depth, epoch/key/policy and freshness across its whole validity interval. If a relay update commits first, finalization referencing the spent state cannot use that snapshot; if finalization commits first, safety depends on W and the stated competing-history observation/settlement assumptions, not transaction priority. Observable unknown ancestry, stale state, unavailable required data or unsupported upgrades pause exit. There is no armed deadline refund, secret-only payout, emergency override or policy migration that rewrites an escrow. These are required changes to `work/r2/settlement-cardano/validators/settlement.ak`, whose Armed/Pending branches currently return false. R1 `outputs/relay-selector/relay-state.ak`, `outputs/anchored-claim`, `outputs/history-prefix/r1-history.mjs` and `outputs/connected-context-transaction/lib/groth_0.ak`/`triple.ak` provide selector, ancestry, tree and pairing patterns; the custom SHA-256 tree and research keys cannot be declared a public bootstrap.
