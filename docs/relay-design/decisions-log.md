## I3 decisions (Mon Nov 2, ~12:56 AM ET)
- **D-16 (F1) PayTag on every payout.** Each payout output carries InlineDatum PayTag{src: OutputReference, n}. Reason: Cardano validators run per-input over a shared tx; without a unique tag one output can satisfy two "pay X to owner" checks (double satisfaction). Tag cost is ~40 B/output; alternative (output-index redeemers) is more fragile.
- **D-17 (F2) Dispute thread token.** anchor3 doubles as minting policy; Open2 mints exactly [header_hash:1] into the dispute UTxO, Resolve2 requires and burns it. Reason: anyone can send a UTxO to the dispute script address with any datum; only a token-authenticated UTxO may affect the anchor. Mutant run confirms the exploit without it.
- **D-18 (F3, refines D-14) Redeemer binding.** Dispute payout paths require the co-spent anchor input's redeemer to be Resolve2 with dispute_ref == own_ref, not just any anchor co-spend. Reason: stops a second dispute piggybacking on another resolve without the anchor ever learning its outcome.
- **D-19 (F4) Reveal must be signed by dd.proposer.** Reason: otherwise the challenger can "reveal" garbage itself and then prove fraud. Mutant run confirms.
- **D-20 (F5, refines D-13) Payouts decided only by anchor3.Resolve2.** Challenger win: whole pot to challenger, entry and all later entries dropped, undisputed dropped entries refunded with tags. Proposer win: proposer gets pot − bond_p, bond_p stays as the entry's bond in the anchor, since := lower (D-12). Orphan: winner takes pot, anchor unchanged. Reason: a single decision point means value is conserved and dispute3 cannot disagree with the anchor.
- **D-21 settle3 reads Anchor2Datum.canonical** (reference input with anchor NFT). Closes the v1 AnchorDatum gap.
- **D-22 Register ≤ 8 headers/tx.** 14,456 B [E] of 16,384; a 9th header (+~1,490 B) would give ~15.95 KB [E], under 450 B of headroom, too tight for signatures/collateral variance. Kept 8 (not measured at 9).

## I4 decisions (Mon Nov 2, ~1:05 AM ET)
- **D-23 MMR over header hashes, bagged root in summaries.** Branch datum holds full peaks (needed to append); anchor/queue entries hold only blake2b(peaks) (32 B) and proofs supply peaks. Reason: removes the 16-batch window (which made 330 confirmations unprovable), keeps the anchor datum small (8 queue entries × 32 B vs × ~600 B). Reason: v2 merkle_verify ignores high index bits → arbitrary confirmation inflation. - **D-36 (replaces D-29) No bond escalation. Parallel disputes + FIXED challenge window + flat bonds + proposer compensation only.**
  Question asked: who pays an escalating bond? First principles: escalation counted per entry is paid by *whoever opens the next dispute*. A fraudulent proposer can self-dispute the valid headers of its own fraudulent entry (it reveals honestly and wins back the bond, so this costs it only fees in D-29 as drafted) and push the bond up until the honest watcher who must dispute the one fake header cannot afford it → fraud finalizes. - **D-42 No frost-core fork. FROST DKG (library) + custom 3-round adaptor signing on the DKG shares + library FROST for the refund.**
  First principles: the two dangers in a 2-party Schnorr adaptor are (1) rogue keys (a party picks its key after seeing the other's, so the plain sum ak_A + ak_B is controlled by one side; demo [M]) and (2) adaptive nonce choice across concurrent sessions (ROS/Wagner). (1) is solved by a proof of knowledge of each key share, which the library FROST DKG already gives us. (2) is solved for 2 parties by committing to nonces before revealing them (3 rounds, the Bellare–Neven/MuSig-1 pattern), which is sound for concurrent sessions given PoK'd keys. FROST's 2-round binding-factor trick only saves a round; with 2 parties and minutes-long swaps a round is cheap. Forking frost-core to add an adaptor point to the binding/aggregation path would mean touching audited code (needs a re-audit) for no security gain. So the cheaper sound option is the custom 3-round scheme on library-generated shares, using only the public serialisation API (no fork).
  Consequence: D-32's "strictly sequential sessions" restriction is lifted *for the 3-round scheme* (still: fresh nonces per session, never resume an aborted session, D-33). The old plain-sum keygen in redpallas_adaptor is retired (rogue-key demo).

- **D-66 v8 design from first principles: dispute threads are unique, conserved and only created by LOpen (~4:15 AM ET).** The invariant the dispute game needs is: *every UTxO the lane/anchor/dispute validators treat as a dispute was created by a genuine LOpen, and its phase/deadline were written only by the validators.* The v7 bug was that the authenticator (the token) was not unique, so it was not conserved one-to-one with disputes. Changes (core8.ak → e2e8_template.ak):
  1. **Unique by construction:** thread name = `blake2b_256("dsp" ‖ src.txid ‖ src.idx (2 B) ‖ entry_id ‖ hh)`, where `src` is the lane UTxO the LOpen spends. - **D-72 RV4-M2 (sockpuppet self-kill), decided from first principles: kill_fee 250 → 900 ADA; challenger reward R = bond_p − kill_fee = 100 ADA.**

  - **Option B, R = 0 (kill_fee = bond_p):** self-kill gives no discount at all, but then honest watchers have no reward at all, only their bond back.
  - **Choice: R = 100 ADA (kill_fee = 900).** R must only cover a watcher's real costs (≈ 1–2 ADA fees [E] and ≤ ~13 h of bond_c lockup), not be a profit centre. Self-kill now gives the fraudster back only 100 of 1,000 ADA, so a fraud attempt costs ≥ 900 ADA whoever kills it (3.6× v8). The natural watchers (swap parties whose funds depend on the relay) are motivated without R.
  - **The safety property is unchanged:** a fraud entry can never finalize against one honest watcher. M2 is an incentive and griefing-price issue only.
  - **Honest flows unchanged except the kill payout:** the challenger now gets pot + 100 ADA = 350 ADA on the s47 Kill [M]. The drop_fee stays 250 ADA, because a dropped entry was valid but out-worked, not fraud; drops are priced by the D-50 paid stall.

- **D-80 — Self-review SR-H1 (High, liveness; also present in v9).** A valid-PoW stale tip plus a young fake entry behind it blocks every drop, so the stale tip finalizes and the append-only relay freezes forever.
  - Fix: new action `Rollback6`. It needs an empty queue and 1 ≤ j ≤ 24, binds the ancestor peaks and tip leaf against the canonical MMR, burns drop_fee, and keeps chainwork.
  - It is safe because rollback_max (24) is less than min_conf (330/990), and the next dispute range starts at A.height.
  - Rejected alternatives:
    - Relaxing the drop rule: it still loses the 1-hour race, because the attacker can hold O non-idle and then finalize it.
    - k-buried truncated checkpoints: a larger ripple through all the tests.
- **D-81 — Fuzz z1101_0160 / z1102_0160 (Low).** `sink_paid` now requires the exact sink address (no stake part), ADA only and no reference script.
  - Before this, burned ADA could be staked for the attacker's reward account.
- **D-82 — Self-review of D-80: chained rollbacks.** Rollback6 now also references the checkpoint UTxO of the current canonical (`cref`), and its datum must equal the canonical exactly.
  - A rolled-back canonical keeps the old chainwork, so its datum never matches a checkpoint. That allows at most one rollback per finalized tip, so the canonical never falls more than 24 leaves below the latest checkpoint.
  - Before this, rollbacks could be chained through empty-queue moments to any depth, for 250 ADA each.
  - Checkpoints are never spent. Settlement (ProveR/ProveC with depth ≥ 330/990, and Arm with any checkpoint of height ≥ rel_height) never reads the anchor, so no rollback can remove or invalidate a checkpoint a swap depends on.
- **D-83 — Settlement against a rolled-back (non-canonical) checkpoint: harmless. No code change; this is a parameter rule.** [E, paper]
  - Every checkpoint was finalized only after its full dispute window, so every leaf in it has valid PoW (I6).
  - Rollback6 creates no checkpoint. It only lets the canonical drop ≤ 24 leaves (D-82) of a tip that may be a stale but valid fork.
  - So a ProveR/ProveC cites a checkpoint whose stale suffix is ≤ 24 blocks (natural forks are far shorter under A3). The proven block then has real-chain depth ≥ min_conf − 24: **306 pre-NU7 and 966 post-NU7**, instead of 330/990.
  - That is theft- or wrong-refund-relevant only under a natural reorg deeper than 306/966 blocks, which A3 already excludes, with a margin of ~7 % / ~2.4 %.
  - Arm only uses checkpoint height ≥ rel_height as a progress signal. Stale blocks are real work at real heights, so the signal is not overstated.
  - **Rejected:** requiring a canonical-lineage checkpoint. Settlement would have to read the contended anchor (contention plus the RV5-L2 liveness risk), and in-flight proofs would break on every rollback.
  - **Rule:** choose min_conf ≥ (A3 depth) + rollback_max. The defaults 330/990 keep 306/966 effective.
