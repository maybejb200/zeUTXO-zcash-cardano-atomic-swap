# zeUTXO audit: private ZEC <-> ADA atomic swap (read-only)

Prepared Sunday Nov 1, 2026 (America/New_York) for John. I only read files on GGLori. I did not run any builds, tests, proofs, launchers or nodes, and I did not modify anything. I did not open any keys, witnesses, seeds, nonces, wallet files or ceremony files. I read Markdown reports plus two small VM-config JSONs. Each claim below names the document it comes from. Anything I inferred myself is labelled **[auditor view]**.

## 0. One-page summary

- **The product:** Alice trades ADA (Cardano's coin) for Bob's ZEC (Zcash's coin). The ZEC stays in a Zcash *shielded pool*, the private part of Zcash where amounts and addresses are hidden. There is no trusted middleman. If the trade fails, each side gets its original coins back without needing the other's help.
- **The core technical fact:** Zcash shielded coins can't carry the scripts or time-locks that a classic "hash-time-locked" swap (HTLC) depends on. So the conditional logic has to live somewhere else. The project tried two places:
  - **R1** put it on Cardano: a Cardano contract that checks Zcash's blockchain itself, meaning a light client. That needs Zcash's proof-of-work (Equihash) and history to be verified cheaply inside Cardano.
  - **R2** used a small transparent (public) Zcash input to get a refund time-lock, plus a hash secret shared across both chains.
- **R2's local swap worked.** Seven of twelve milestones are complete locally. It was stopped by a timing question, not by a broken mechanism. Every HTLC-style swap assumes each transaction gets mined within a known deadline. The project's own safety gate refused to accept that assumption without a written, numeric residual-risk criterion, and no one ever wrote one (R2-M10-VIABILITY-DECISION.md).
- **The redesign went back to R1's problem.** To survive arbitrarily long delays, the "stronger settlement" redesign made Cardano pay out only against a cryptographic proof of the Zcash outcome. That brings back the trustless Zcash-on-Cardano relay, which is the very thing R1 had been archived over. R2's own founding documents listed that as a stop condition (NEXT-ROUTE.md; R2-DESIGN.md).
- **Even then, timing isn't gone.** The redesign still relies on honest watchers delivering competing-chain data within a challenge window W. No number for W could be justified (R2-SETTLEMENT-DESIGN.md; R2-OPERATING-DECISION.md D1 annex). The timing assumption moved from the two traders to the relay watchers, at a much higher engineering cost.
- **The proof engineering hit a wall.** The design checks a STWO proof inside Groth16 proofs, split into **652 fixed proof positions**. Only one leaf proof and one parent proof were ever produced. The latest producer attempt finished setup (2,188.77 s) and then ran out of memory on its first 256 MiB buffer, at a peak of 6,771,428 KiB under a self-imposed 8,500,000 KiB cap (R2-QUOTIENT-COMPACT-BACKEND.md). An older R1 calculation was "about 162 years" to bootstrap from Zcash genesis, but the docs present it only as an illustration (R2-OPERATING-DECISION.md D1 annex).
- **Most of the hard blocks are self-imposed or framing-driven, not mathematical.** The strongest drivers are:
  1. Safety under *unbounded* delay.
  2. No trusted party, committee or checkpoint, and bootstrap from Zcash genesis.
  3. Original-asset unilateral refunds.
  4. A ~8.1 GiB memory cap, two Go threads and "no hardware spending" by default.
  5. One proof stack (gnark Groth16 over BLS12-381, which needs a trusted setup for each circuit) wrapping STWO.
- **Not considered in the docs I read:** a federation or committee, optimistic bonded header relays, or the owner-approved fallback. The first two were either rejected without costing or never examined. The owner-approved fallback was designed but never offered as a product choice. I found no hits at all for "optimistic", "BitVM" or "federat", and nothing on GPU proving.
- **Path drift:** every document points at `<WIN_HOME>\...`, which doesn't exist on GGLori (the Windows user name there differs). The working copies are `C:\HyperV-Workspace\R1` and `R2`, which appear to have been copied there tonight (Nov 1, ~10:51–10:57 PM ET). The transparent MVP exists only as an earlier-dated copy under `<WIN_HOME>/Documents/Codex/2026-09-05\can\outputs\zec-cardano-lab`.

## 1. The actual goal and the self-imposed non-negotiables

**Product requirement, in plain words.** Alice holds ADA and wants ZEC. Bob holds ZEC and wants ADA. They should be able to swap directly with these properties:
- Bob's ZEC moves only inside a Zcash shielded pool (Ironwood, the newer v6 shielded pool).
- Alice receives ZEC she can independently spend.
- No exchange, custodian, oracle, committee or relay signer has to be trusted.
- Either both get paid, or both get their own original coins back without the other's cooperation.
- It should work on public testnets first, ideally completing in about 30 minutes, running on the owner's own machine.

Sources: THREAT-MODEL.md (R1), PROJECT-DECISION.md (R1), R2-M10-VIABILITY-DECISION.md, R2-SETTLEMENT-DESIGN.md.

**Non-negotiables the project imposed on itself** (quoted or closely paraphrased):

| # | Constraint | Where it is stated |
|---|---|---|
| N1 | "Preserve automatic outcome settlement with independently authenticated source history." Owner-approved settlement must not be silently substituted. | AGENTS.md (R2) |
| N2 | No trusted coordinator, relay, proof server or committee. If one becomes necessary, "record the changed trust model and fail the default gate." | THREAT-MODEL.md (R1); R2-SETTLEMENT-DESIGN.md |

## 2. Timeline

Dates are 2026, as given in the docs.

### 2a. Transparent MVP, around Sept 5–7
Location found: `<WIN_HOME>/Documents/Codex/2026-09-05\can\outputs\zec-cardano-lab\README.md`. The docs cite it as `...zec-cardano-transfer-2026-09-07\zec-cardano-lab`.

- **What it tried:** a classic HTLC. Alice locks ADA in an Aiken/Plutus V3 contract keyed to SHA256(S). Bob locks *transparent* ZEC in a P2SH script with the same hash plus a CLTV refund. Alice claims ZEC and reveals S; Bob uses S to claim ADA. (docs/ARCHITECTURE.md)
- **What worked:**
  - Confirmed public-testnet trials: a Cardano Preview lock and claim, a transparent v4 Zcash lock and claim, and a separate refund trial.
  - 80 passing checks; ZIP-243/244 test vectors pass. (README.md)
- **What stopped it:**
  - It wasn't private. The public hash links the two legs, and the ZEC is transparent.
  - Its own architecture note says it "is not safe under indefinite outages" (docs/ARCHITECTURE.md). The later projects treated that same timing property as disqualifying.
- **Adaptor-signature document:** a docs/SHIELDED-ADAPTOR-SWAPS.md proposed adaptor signatures with "zero cross-chain linkability". R2-DESIGN.md later says that claim "is not reusable evidence". R2-SAFETY-SOLUTION-RESEARCH.md, citing the COMIT paper, notes that adaptor signatures don't fix disclosure-before-confirmation.

### 2b. Research shortlist (Sept 6–7) and R1 (until Sept 10, archived no-go)
Sources: FEASIBILITY.md, ALTERNATIVE-CONSTRUCTIONS.md, THREAT-MODEL.md, PROJECT-DECISION.md, NEXT-ROUTE.md, stwo-wrapper-review/MVP-FEASIBILITY-DECISION.md.

**Shortlist** (ALTERNATIVE-CONSTRUCTIONS.md):
- R1: proof of completed payment.
- R2: shared transparent auxiliary input.
- R3: deferred ADA payout with a refund challenge.
- R4: timed release of the refund authorization.
- R5: Cardano reveals a missing key share. Rejected.

**R1 idea:** ADA locks first. Bob makes an ordinary shielded payment to Alice. A zero-knowledge proof, checked on Cardano, shows that the payment is in the authenticated Zcash chain, and that releases the ADA. No joint ZEC custody is needed. The catch is that Cardano must authenticate Zcash's chain trustlessly, from genesis.

**What worked:**
- A full integrated local regtest/emulator swap with 25 header proofs and three receipt proofs.
- One recursive verifier proof: 2,359,573 constraints; 2,475.57 s setup; 102.60 s proving; 4.93 GiB peak.
- Equihash(200,9) as a circuit: 26,650,078 constraints. A staged version uses four 8,212,125-constraint leaves plus a 7,152,467-constraint global relation (DESTINATION-CHECKPOINT.md).
- A legacy direct-header benchmark: 5 proofs per header, 701.34 s plus 129.79 s parameter loading (PROJECT-DECISION.md).

**What stopped it** (PROJECT-DECISION.md, MVP-FEASIBILITY-DECISION.md):
- Full verifier modelled at 151.4–155.6 million constraints for FRI plus composition hashes alone.
- Full-memory kernel setup failed three times at the 10,500,000 KiB cap.
- Chunk composition was not authenticated.
- Staged on-chain verification would need 64–66 submissions per header.
- Bootstrap from genesis is impractical; the historical straight-line figure is 4,336,164 headers and about 162 years at 1,179 s per header (cited in R2-OPERATING-DECISION.md as an illustration, not a forecast).
- A direct Equihash checker on Cardano exceeded the budget at 19.28 billion CPU units (DESTINATION-CHECKPOINT.md).

**Decision:** HOLD/no-go for the 30-minute prototype. "Technical possibility is unresolved, rather than disproved."

### 2c. R2 (Sept 10–27, paused Sept 27)
Sources: R2-DESIGN.md, R2-COMPLETION-CHECKLIST.md, R2-M10-VIABILITY-DECISION.md, R2-SAFETY-SOLUTION-RESEARCH.md, R2-PUBLIC-PROFILE-ASSESSMENT.md, R2-SETTLEMENT-DESIGN.md, R2-PROOF-FEASIBILITY.md, R2-SETUP-WORK-ASSESSMENT.md, R2-QUOTIENT-COMPACT-BACKEND.md, R2-OPERATING-DECISION.md.

**Phase 1 (Sept 10–12): shielded HTLC variant**
- The ZEC principal sits in a 2-of-2 FROST/RedPallas jointly controlled Ironwood note, plus a small transparent P2SH "auxiliary" output. That output supplies a hash branch and a CLTV refund branch; both require both signatures.
- A pre-signed shielded refund is prepared before funding. The ADA side reuses the MVP's hash-lock validator.
- The project explicitly accepted that the cross-chain hash link makes the two legs linkable (R2-DESIGN.md).
- **Worked locally:** M01–M07 complete within local scope (R2-COMPLETION-CHECKLIST.md). That covers:
  - shielded swap and refund;
  - separate signers;
  - crash and submission recovery;
  - fixed-fee lifetime checks;
  - service, node and machine restart;
  - partial-transaction repair.
- M08 P2 (local separate-UID owners with DKG) is also done.

**Phase 2 (Sept 12–13): safety finding**
- A fixture that withheld delivery of Alice's claim let Bob take the ADA and also refund his ZEC (R2-DESIGN.md; R2-M10-VIABILITY-DECISION.md "saved loss trace").
- The review also found the reverse risk: Alice can hold a valid ZEC claim until the last moment, refund ADA, and still claim ZEC.
- Verdict: public MVP **NO-GO**. Classic swap literature (Herlihy) assumes a known publish/confirm duration; the project had no defensible public bound and no accepted risk criterion.
- The single public profile assessed (Zcash testnet + Cardano Preprod) was rejected. It had six port gaps, for example:
  - DKG works over loopback only;
  - one ADA service holds both wallets;
  - native funding hard-codes `coinbase.bin` and expiry 48.
  (R2-PUBLIC-PROFILE-ASSESSMENT.md)

**Phase 3 (Sept 13): stronger settlement design**
- Armed ADA may exit only against an *authenticated Zcash claim or refund outcome*. Time alone can never release it.
- That outcome comes from a permissionless header relay on Cardano with a challenge window W.
- A finite-state model check passed: 10 configurations, 3,762 states, 10,357 edges, 7 deliberately weakened configurations all fail as expected.
- An **owner-approved fallback** (each owner signs the ADA release that could hurt them) was specified. It was labelled "not an equivalent completion of the original atomic-swap MVP" and was not offered as the product (R2-SETTLEMENT-DESIGN.md).

**Phase 4 (Sept 13–27): Cardano core and proof decomposition**
- The settlement-core contract compiled, but all Armed/Pending exits are disabled ("do not fund or arm").
- Source authentication was decomposed into **652 fixed proof positions** (STWO verifier pieces wrapped in Groth16).
- Real proofs: one role-47 leaf (211,230 constraints, 489 s setup, 25 s prove) and one optimized parent (2,957,922 constraints, 3,304 s setup, 197 s prove, 6,081,888 KiB RSS) (R2-PROOF-FEASIBILITY.md; R2-SETUP-WORK-ASSESSMENT.md).
- An earlier parent setup timed out at 59m40s.
- The quotient producer (4,517,360 constraints) completed setup (2,188.77 s), then hit out-of-memory at its first 256 MiB H buffer: 6,771,428 KiB RSS with 6,911,492,096 bytes in use. Zero quotient proofs were produced (R2-QUOTIENT-COMPACT-BACKEND.md).
- The AI-account allowance hit 100% (R2-QUOTIENT-COMPACT-BACKEND-USAGE-ADDENDUM.md).

**Phase 5 (Sept 27): assessment and D1 park**
- The operating decision stopped further optimization and ran one capped design pass (D1) comparing two routes: (A) R1's direct-header route and (B) R2's composition reorganized into bounded key families.
- **Both were parked**, because neither has "a credible complete bootstrap/service/resource/security case."
- The user paused the project the same day.

## 4. Framing critique

### 4.1 Which assumptions caused the hardest blocks [auditor view, built on the docs]

1. **"Safe under arbitrary delay."** This single requirement turned a working local HTLC swap (M01–M07) into a demand for a full trustless Zcash light client on Cardano. R2-M10-VIABILITY-DECISION.md is explicit about the fork in the road:
   - If a bounded risk model is accepted, R2's shared-secret design remains "the smaller engineering route".
   - Only if "the requirement is asset preservation despite arbitrarily long post-disclosure delay" does the settlement need a redesign.

   The redesign was chosen. But the owner was never shown a concrete residual-risk number to accept or reject. The docs say so: "Neither a numerical residual-risk threshold nor acceptance of one is documented."

2. **The redesign brought back R1's dependency.** NEXT-ROUTE.md recommended R2 precisely to *avoid* proving the Zcash relay on Cardano, and said to "Reject any return to the unresolved R1 relay as an unacknowledged dependency". R2-DESIGN.md says to stop the candidate if it "require[s] the unresolved R1 on-Cardano Zcash relay". The stronger settlement design did exactly that; R2-M10-VIABILITY-DECISION.md acknowledges it "revisits R1's unresolved verification and cost obligations." So R2's later proof work is effectively R1 again, with extra obligations on top (joint custody, arming).

3. **It doesn't actually remove timing assumptions.** The stronger design swaps "Alice's claim is mined in time" for "an honest watcher sees and proves any competing heavier Zcash fork within W". Neither is bounded by evidence (R2-SETTLEMENT-DESIGN.md; D1 annex: "watcher/challenge assumptions remain mandatory"). The cost went up by orders of magnitude, but the kind of assumption didn't change. **This is the most important framing finding.**

4. **No trusted checkpoint, bootstrap from genesis.** This forces proving millions of historical headers (the 162-year illustration). Deployed light-client bridges commonly start from a socially agreed checkpoint. The docs reject that ("A recent trusted checkpoint is not implicitly authorized", relay-certificate-design.md) without costing the trade-off.

5. **No committee or federation.** The docs dismiss a witness committee as "substitutes additional trust" (R2-M10-VIABILITY-DECISION.md) and AC3WN as adding assumptions (R2-SAFETY-SOLUTION-RESEARCH.md). No trust-minimized committee variant (threshold, bonded, slashable, multi-operator) was ever designed or costed.

6. **Resource envelope and proof-stack lock-in.** A ~8.1 GiB cap and 2 Go threads; Groth16 (gnark, BLS12-381) wrapping STWO; and "Do not start a third backend, a new general proof framework or a wider literature survey" (R2-OPERATING-DECISION.md). These kept the investigation bounded, but they also mean the proof-system space was never re-opened after R1.

7. **Original-asset unilateral refund (N4).** This excluded the owner-approved fallback, which needs no cross-chain verifier at all. It also excluded penalty- or collateral-based designs.

## 5. Open questions for the research phase

**Product and risk**
1. Is "safety under arbitrarily long delay" a real requirement for you? Or would a written residual-risk criterion be acceptable — for example, "loss only if Zcash or Cardano inclusion is delayed beyond X hours with Y% fee headroom"? This one decision chooses between the R2 HTLC route, which is mostly built, and the light-client route.
2. Would you accept a **bounded trust** model? Options include:
   - a k-of-n bonded, slashable committee attesting to Zcash outcomes;
   - a socially agreed relay checkpoint instead of genesis;
   - owner-approved settlement with a penalty or collateral to deter withholding.

   For each: what does it cost, and what does it protect against?
3. How much privacy is actually required? Is cross-chain linkability via a shared hash acceptable (R2 already accepts it)? Is hiding the amount required?
