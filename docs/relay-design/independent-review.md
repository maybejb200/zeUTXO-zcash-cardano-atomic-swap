## CRITICAL

### C-1. `ProveLeaf` accepts out-of-range positions, so a challenger wins against an honest header **[M]**

**Evidence**
- `zeutxo-step1-relay-cost/aiken/lib/zrelay/equihash.ak:143-151`:
  ```
  pub fn prove_leaf(header, root, p, leaf, path) -> Bool {
    leaf_in_root(leaf, p, path, root) && leaf != leaf_value(header, index_at(header, p))
  }
  ```
  - `leaf_in_root` uses only the low 9 bits of `p`, through 9 path steps.
  - `index_at(header, p)` reads bytes past the 1,344-byte solution for p ≥ 512. Aiken's `slice` clamps an out-of-range read to empty, and an empty read decodes to index **0**.
  - So `p' = p + 512` verifies the **true** leaf at p against the root and compares it to `leaf_value(index 0)`. Those differ, so "fraud proven".
- It is called unchecked from `e2e4/core4.ak:488-495` (dispute4) and **is still present in the new `e2e5/core5.ak:493-498`** (dispute5). `equihash.ak` is unchanged.

**Test (my scratch copy)**
- `zeutxo-review-scratch/t1/lib/zrelay/rv1_test.ak`, generated by `gen_rv1.py`, uses real mainnet header 3538808:
  - honest reveal ok;
  - in-range control rejected;
  - p+512 **accepted**;
  - p+1024 **accepted**;
  - `index_at(589) == 0`.
  - 5/5 pass [M].
- Validator level: `t1/validators/rv2.ak`, generated by `gen_rv2.py`, is the author's own `s28` transaction (honest reveal D2, real header 3538896, root `691bab…`) with Timeout replaced by `ProveLeaf{p = 77+512}`.
  - The dispute4 and anchor4 scripts **pass** [M].
  - Result: the challenger receives 1,250 ADA (its own 250 bond plus the honest proposer's 1,000), honest entry A and its descendant B are dropped, and the queue is emptied.
  - Cost: 4,715,933 mem / 4,430,268,387 CPU [M, unit context].
- Fix check: in `t2/`, adding `p >= 0 && p < 512 && bytearray.length(header) == 1487` makes both exploit tests fail and the honest and control tests pass [M].
  - I did not re-run the author's full e2e suites with the fix.

**Exploit sketch**
1. Watch for any honest proposal.
2. Open a dispute (250 ADA) on any header in it.
3. Wait for the honest Reveal.
4. Submit ProveLeaf with p+512.
5. Win the bond and drop the entry plus everything after it.

Repeat forever. Each round is profitable (+1,000 ADA minus fees), so the relay never finalizes anything honest. That blocks ProveC and ProveR, and feeds M-1 and H-2 (stalls that end in Release or Fallback theft).

**Fix**
- Range-check `0 ≤ p < 512` in `prove_leaf`.
- Range-check `a, j` the same way in `prove_index_order` (dup is already checked).
- Require `length(header) == 1487` in every Prove*.
- Add the two negative tests above to the regression suite.

### C-2. Anchor-UTxO contention lets an attacker censor all disputes cheaply, so a fake fork finalizes **[E]**

**Evidence**
- In e2e4 (and e2e5's same structure), every `Open4` spends the single anchor UTxO and must land with `upper ≤ since + W_c` (`core4.ak:282-325`).
- `Propose4` (`core4.ak:224-265`) may drop trailing entries with `open == 0`. It refunds their bonds **in the same tx** (`refunds_ok`) and needs no signature from the dropped entry's owner.
- `Finalize4` (`core4.ak:266-281`) can be called by anyone once `lower ≥ since + W_c`.
- D-36 prices the "residual race" at ≈263k ADA, assuming each blocking spend forfeits 225 ADA. That assumption is wrong.

**Exploit sketch**
1. The attacker proposes fake entry F, a heavier fake fork, after the honest tail.
2. For the next W_c = 6.5 h (≈1,170 Cardano blocks at ~20 s [E]), the attacker keeps a chain of anchor spends always ahead in the mempool. Each is a `Propose4` adding a slightly heavier fake tip G_k that **drops its own previous G_{k−1}**. Its bond comes back immediately.
   - In v5 a new tip needs one more free fake header (H-3). In v4 it needed one sha256d grind of ≈2^41.
   - An alternative is a bond-neutral self-dispute on its own trailing fake G (Open, then ProveDup on a deliberately duplicated index; the challenger wins its own bond back).
3. An honest watcher's Open must spend the same UTxO. On Cardano the chained tx that's already propagated wins the first-seen conflict, so the attacker wins most races [E]. This is probabilistic, but strongly attacker-favoured, and more so for an SPO or anyone with a mempool or relay edge.
4. After W_c the attacker calls Finalize on F. Canonical is now fake.
5. The attacker publishes a fake block containing txid_R or txid_C. Both parties know the txid and salt behind `c_com`/`r_com`. They then ProveR or ProveC with ≥330 fake confirmations and take the ADA, after already holding or refunding the ZEC.

**Cost [E]:** fees only, ~1,170 × (Propose + 1-header Extend) at roughly ≤2 ADA each, so ≲2.5k ADA. Min-UTxO deposits on branch UTxOs are temporarily locked but recoverable. That is about two orders of magnitude below the 263k ADA in D-36. I have not measured the Propose or Extend fee for 1 header.

**Fix**
- Make disputes not touch the global anchor. Give each entry its own dispute-lane UTxO, or have Open create a dispute UTxO that only references the anchor; Finalize then checks for the absence of open disputes via a counter in the lane.
- Delay refunds of dropped bonds until after W_c.
- Forbid dropping entries younger than W_c.
- Extend W_c automatically when the anchor saw more than N spends in the window.
- At minimum, re-derive the D-36 race cost with bond-neutral blocking moves included.

## HIGH

### H-1. X's CLTV branch is spendable by Bob alone, which destroys both C and R **[E]**

**Evidence**
- `zeutxo-step2-adaptor-spec.md` gives the X script: `IF 2 K_A K_B 2 CHECKMULTISIG ELSE T_B CLTV DROP K_B CHECKSIG`.
- `settle4` (`core4.ak:546-615`) only knows `c_com` and `r_com`, i.e. txids of the specific C and R.

**Exploit sketch**
1. After T_B, Bob spends X with his own tx X' (not R).
2. C and R both become permanently invalid, because they spend X, so neither ProveC nor ProveR can ever succeed.
3. If the swap is in `Pending` (Bob claimed), Bob waits for `Release` and gets the ADA.
4. N (the 2-of-2 note) stays frozen. Bob can later extort Alice to co-sign its spend.

**Fix**
- Make X 2-of-2 only (no unilateral branch).
- Have R pre-signed by both parties with nLockTime T_B, so the only possible spends of X are C or R, and every spend is provable on Cardano.
- Alternatively, have Cardano accept a proof of *any* spend of X after T_B, in favour of Alice.

### H-2. "H2 removed" is not true: Bob can get both assets when C is late **[E]**

**Evidence**
- `settle4` gives `release_at = t_a + pending_ms` (author's settle.ak test datum: `pending_ms = 90,000,000 ms = 25 h`).
- The architecture doc's budget is ≈ T_B + 2.3 h + 7 h + D.
- Release is allowed at `lower > release_at`. ProveR is allowed in any phase.

**Exploit sketch**
1. Alice's C misses T_B, so Bob gets R mined (ZEC back).
2. Alice must ProveR before `release_at`.
3. Bob, or anyone acting for him, opens one frivolous dispute (250 ADA, of which 225 is lost) on the entry containing R's block, as late as possible.
4. The entry can't finalize until the dispute resolves: up to τ + reveal latency, worst case W_c + 2τ ≈ 18.5 h [E from dispute-design numbers].
5. This exceeds the 7 h lag plus margin, so Release fires and Bob holds ZEC plus ADA.
6. With C-1 the dispute even pays Bob.

**Fix**
- Budget `release_at ≥ T_B + 330·25 s + proposal cadence + W_c + 2τ + 2D`, plus a contention margin.
- Or extend `release_at` automatically while an entry above R's height has open disputes (read from the anchor).
- Or drop Release in favour of ProveC-only payout plus Fallback.

### H-3. Compressed headers (v5, D-43) make fake headers free **[M-author / E]**

**Evidence**
- `aiken/lib/zrelay/header_c.ak:79-125` checks per header only linkage, version, time, DigiShield bits and `hash ≤ target` on a **claimed** hash (`chunk_hashes`, line 128).
- `sha256d(prefix‖sol) == hash` is checked only in a dispute (`reveal_binds`, lines ~199-204).
- The author's own test `fraud_c_fake_intermediate_hash_accepted_on_chain = pass` [M-author, compress/c_measurements.tsv].

**Assessment**
- The binding is correctly restored *inside* a dispute:
  - the MMR leaf is `blake2b(prefix‖hash)`;
  - Open5 pins the prefix and hash (`core5.ak:305-306`);
  - Reveal must produce a matching 1,344-byte solution;
  - settlement recomputes `header_leaf` from a full header.
- So the 140-byte format does **not** lose binding the relay needs, as long as every fake header is disputed.
- But the 2^41-sha256d grinding cost that dispute-design.md relied on is gone. Fake forks of any length now cost only fees.
- Safety is therefore entirely the dispute game: liveness of at least one watcher, no censorship (C-2) and correct Prove* code (C-1). Docs that still cite grinding as a barrier are out of date.
- My earlier note that "no short-header artifact exists" was true for the 01:40 snapshot only. The files were re-created at ~01:45 (D-47).

**Fix:** fix C-1 and C-2 first. Consider requiring the full header (or a random sample of solutions chosen by a later block hash) for the last header of each batch, to restore some per-batch PoW cost.

## MEDIUM

### M-1. Fallback theft: Alice stalls the relay until `t_fb` **[E]**
- If Bob's Claim misses T_A, Alice takes C (the ZEC) and can stall all finalization until `t_fb = release_at + 7 d` by keeping fake forks in front of honest entries.
- Under flat bonds this costs ≈1,000 ADA per fake round, ×~9 rounds over 7 d ≈ 9k ADA [E]. With C-1 or C-2 it is close to free.
- Fix: as in C-2. Also make Fallback require proof that R was *not* mined (impossible directly), or make `t_fb` effectively unbounded unless the relay is live.

### M-2. Bob must verify the escrow before Claim **[E]**
- Bob must check:
  - the settle4 script hash, including params `anchor_policy` and `base`;
  - every datum field: `c_com`/`r_com` with his salts, `min_conf = 330`, `pending_ms`, `t_fb`, `pkh_*`, `p_a`.
- If he doesn't, Alice deploys with a rogue `anchor_policy` and "proves" R against her own fake relay.
- The spec does not list this check. Add it to the protocol and to swap_e2e as a negative test.

### M-3. 3-round adaptor on FROST shares (D-42) **[E]**

**Code reviewed:** `frost_2of2/src/bin/frost_adaptor.rs:81-110`. The math is correct [M-author run: ALL_OK = true]:
- R = R_A + R_B + T_p;
- c = H*(R‖rk‖sighash);
- z_B = k_B + c·λ_B·s_B, with λ = (2, −1) correct for ids {1, 2};
- Alice's α term goes into z_A;
- pre-verification against Bob's verifying share is correct;
- Bob cannot complete without z_A;
- even-y normalisation is consistent.

**Concurrency / ROS:** commit-then-reveal nonces (MuSig-1 / Bellare–Neven style) do block Wagner/ROS. That relies on Bob refusing to reveal R_B in *any* session before holding Alice's commitment for that session. The adaptor point is Bob's own, so adding it is fine. D-42's claim is plausible but unproven.

**Gaps:**
1. `com()` binds only a random `session` id, not (sighash_c, rk/α, T_p, ak, swap id).
   - If an implementation lets Alice change α or the sighash after round 2 and re-requests z_B with the same nonce, two z_B values under one k_B leak s_B. Alice would then hold both shares and could spend N alone.
   - Fix: session = H(swap_id‖ak‖rk‖sighash_c‖T_p), delete k_B immediately after use, never retry a session.
2. The same DKG share is used in the custom protocol and in library FROST (refund R). That cross-protocol security is not analysed. Use domain-separated derived shares if possible, or document the argument.
3. Extraction runs Cardano → Zcash only: Alice extracts t from Bob's completed BIP-340 sig.
   - `bip340_adaptor.py` handles odd-y R by negating, and I verified the algebra [E].
   - The trusted `neg` flag in preverify is harmless.

### M-4. Dispute timing not budgeted **[E]**
- Each entry can be stalled W_c + 2τ by a single 250 ADA bond.
- A fork replacement drops honest entries. Bonds are refunded, but the honest entries must be re-proposed and their W_c restarts.
- Neither effect is included in the `release_at` or `t_fb` derivations.
- An honest proposer must land its Reveal within τ (6 h). That's fine, but it competes for the anchor under C-2-style contention only at Resolve.

## LOW
- **L-1** `mmr.ak` bag = blake2b(concat(peaks)) has no length or count binding. Not exploitable given the fixed 32-byte peaks and the sha256d/blake2b domain split. Still, add a count prefix.
- **L-2** `settle_check` → `merkle_verify` does not length-check the txid, siblings or salt, and does not bind the tx index to path length. Not exploitable for a fixed committed txid; add `length == 32` checks.
- **L-3** `dleq2`:
  - The design is sound: per-bit CDS OR-proofs AND-ed across both groups, PoK forcing zero blinder sums, t < 2^252 below both orders, NUMS H via try-and-increment.
  - It accepts T = identity (t = 0), which harms only the prover's counterparty choice. Reject it anyway.
  - `swap_e2e.py:20` uses a random placeholder ctx. The real swap must bind swap id, both keys, `c_com` and `r_com` (D-34).
  - Proof is 56.8 KB [M-author].
  - No external review yet.
- **L-4** The relay params assume one spacing/window. The NU7-style transition (75 s→25 s, window 17→102) inside a branch is unhandled.
- **L-5** `curves.py` and the Python adaptor are not constant-time and use `secrets` (prototype only).
- **L-6** On challenger_won, sibling disputes on the dropped entry become orphaned. Check that their bonds remain claimable (I did not test this).

## Settlement checks (MMR, reorgs, deadlines)
- Confirmation counting: `proven4`/`proven5` fix the leaf height via MMR index and size (the F6 fix). I found no way to inflate confs on an *honest* canonical chain [E].
- Reorg risk: 330 confs at 25 s ≈ 2.3 h [E]. That's ample against natural Zcash reorgs. The real risk is a fake canonical chain (C-1, C-2, H-3), not a natural reorg.
- Both-assets / loses-both paths found:
  - Bob gets both via H-1 or H-2.
  - Alice gets both via M-1.
  - Anyone can take both after C-2.
  - A party is frozen out of N under H-1.

## Plain-English verdict for John
The cryptography looks right as written:
- the cross-curve proof;
- the Bitcoin-style adaptor on Cardano;
- the math of the FROST adaptor.

The 3-round signing still needs strict session handling, and an outside cryptographer should look at all three.

The swap is **not trustless yet**. The weak point is the Zcash light-client relay on Cardano, where three things are broken:
- A one-line missing range check lets anyone "win" a dispute against an honest relayer. I reproduced this on a real Zcash header, and the one-line fix works.
- The single shared relay UTxO can be hogged cheaply, so honest watchers can be shut out and a fake Zcash history can be finalised.
- Two timing and script details (Bob's solo CLTV branch, and a Release deadline too tight for one cheap dispute) let one side end up with both coins.

All of these are fixable. Do not lock real funds until C-1, C-2, H-1 and H-2 are fixed and covered by adversarial tests.
